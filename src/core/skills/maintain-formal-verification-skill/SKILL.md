# Maintain a formal verification skill

Find the project verifier, its runner, models, negative controls, trace probes and CI entry point. If there is no project verification to maintain, use `create-formal-verification-skill`.

1. Record the current head and working-tree changes. For each property, read its promise, authority, source symbols, last reviewed commit, bounds and assumptions. Run the existing pinned command unchanged and retain its verdict and implementation evidence. If the sync revision is missing, identify the last relevant verification change as a provisional baseline and disclose the uncertainty.
2. Inspect changes since that revision, including uncommitted edits, renames, new writers, callbacks, storage contexts and changes to synchronization. Follow callers beyond the old path list. Reconcile every abstract action with a reachable implementation step. Check whether the trace still observes the guarded state. A green baseline can describe a superseded design.
3. Update verification-owned files when source mappings, atomic steps, configuration, bounds or observation points have drifted. Preserve the original promise unless a contract change has explicit authority. Cite that decision and record the old and new obligations. Explain any reduced bound. Leave product repair to separately authorized work.
4. Run the pinned Everystate gate and its named negative controls. Reproduce the witness with the project’s pinned Everystate configuration and retain the JSON action sequence. Map each step to current code. Drive those events through the implementation, capture ordered JSONL observations, and run Everystate `conform -json -trace run.jsonl Spec.tla` with the same configuration. Record where the witness or the observations first diverge. An impossible step identifies model drift. A reachable violation of an unchanged promise is a product finding; show the witness, harm and introducing revision if established. A runtime conformance mismatch requires checking both the observation and the model. Mark missing runtime evidence as blocked even if the model passes.
5. For each affected check, try its realistic production mutation in a disposable copy. Require the documented runtime trace or regression test to catch it. Restore and rerun the published command. Check that the gate rejects the expected malformed or unexpected verdicts and that CI invokes the same entry point. A model-only mutant demonstrates sensitivity of the model alone.
6. Report each property as in sync, updated, bug or blocked. An updated model can reveal a bug. Give the reviewed range, commands, counterexamples, implementation evidence and outstanding exclusions. Advance the per-property sync revision only for code actually reviewed and checks substantiated at that revision. Retain the previous revision for blocked checks and record the attempted head separately. Keep verification repairs separate from product fixes.
