# Create a formal verification skill

Deliver a repository-local skill that a developer can run after changing covered code. Inspect existing verification commands, CI, skill discovery and models before choosing files. Extend an existing project verifier when it already owns the flow.

1. Start with the requested area or the most consequential ordering-dependent failure you can ground in the code. State one user-visible promise, its authority and the harm if it breaks. Identify all writers, including callbacks, retry and recovery paths. If the question requires unbounded proof, hardware behavior or exhaustive execution of arbitrary code, explain what evidence that requires before claiming coverage.
2. Write a finite TLA+ model and configuration for Everystate. Map each action to a named source symbol. Split actions at observable suspension, transaction and ownership boundaries. Model distinct worker identity even when two workers share a logical key. Include relevant failure paths. Declare the bounds, initial states, environmental assumptions and excluded behavior. For liveness, justify fairness and progress assumptions.
3. Pin a tested checker version. For example, with Node 20+, run `npx --yes everystate@0.4.1 -json Spec.tla` from the model directory. Use the JSON verdict and the process exit code. For an invariant require exit 0 and status `ok` on the healthy configuration. Change one guard in a separate configuration and require exit 12, status `invariant`, and the intended invariant name. Use the appropriate verdict for a liveness or deadlock property. A parse error, timeout or missing binary is a failed gate. Explain each genuine counterexample as a sequence of product events.
4. Connect the check to the implementation. Capture ordered JSONL observations at the production boundary, including action, worker identity and state needed to distinguish correct behavior. Run `npx --yes everystate@0.4.1 conform -json -trace run.jsonl Spec.tla`. Check the verdict, expected observation count, matched count and ignored count. When a trace is impractical, use a deterministic regression test through the real entry point and identify the remaining gap. A hand-written trace only tests the model.
5. Generate the local skill with discovery frontmatter, concrete commands and a per-property coverage record: source paths and symbols, reviewed commit, bounds, assumptions, negative control, implementation evidence and how to interpret failure. Put one runner behind the local verification flow and CI where the project already uses them. A missing required check makes the aggregate fail. Preserve current product failures as findings.
6. Follow the generated instructions from a clean start. In a disposable copy, break the corresponding production guard and run the documented gate. Verify the failure identifies the intended property or behavior. Restore the copy and rerun. If only the model mutation fails, disclose that the implementation link is unverified. Report the actual runs, bounds, findings, and remaining gaps. Revisit the coverage record with `maintain-formal-verification-skill` after covered code changes.

Tool reference: [Everystate formal verification](https://github.com/mattzcarey/everystate/tree/28fd7c5f9069a021b7a9702007e2f2b054a789fb/skills/formal-verification).
