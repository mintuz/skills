# Design loop

Create a design, or raise the quality of an existing design, until it meets a bar that the user confirms. Use it for three entry points: a spec that needs a design, an existing screen to polish, and a feature concept whose design becomes the input for a spec. `gauntlet-loop` owns the bar, the builders, the fresh critics, the verdicts, the ledger and the stop policy: read it before step 4 and follow it from there. This playbook adds the inputs and the hand-over.

Before step 1, check the route. When one design decision is open and everything else is fixed, run Prototype: it settles the decision with throwaway variants behind a switcher and needs no bar. When the open questions are about how a product, a feature or a fix works, not only how it looks, also run Prototype. When code must match an agreed mock-up or design export, run Match design: the agreed design is already the bar, so there is no new bar to iterate toward, and references do not change it. When the user asks for the loop on such a request, name the playbook that applies and say why.

1. **Name the entry point and the scope.** Write the entry point and each screen in scope. For a spec, its states and examples are fixed inputs. For a polish, keep every existing feature, and add a feature only when the user permits it (principle-stay-in-scope). For a concept, the output is a design, not production code.
2. **Capture the starting point.** Capture each in-scope screen and state of the running product with `eyes`: the browser for web, the simulator or the device for iOS (principle-experience-first). For a concept, capture the screens that the feature joins. Start each variant from these captures, not from a memory of the product. Done when each in-scope state has a capture or is marked as new.
3. **Gather the references.** When the host exposes the tools of the Mobbin connector, search real-app screens and flows for the same task, and keep the link of each screen that you pin. When the host does not expose them, state that gap in the plan. Then use the screenshots and the apps that the user names, and the product's own best screens. A reference shows hierarchy and pattern; the product's tokens and components still win.
4. **Set the bar and get it confirmed.** Follow step 1 of `gauntlet-loop` (principle-fix-the-bar-first), and write the bar in this form:
   - **Criteria:** turn "world class" or "worthy of an Apple Design Award" into named criteria that a critic can check against the pinned references, for example hierarchy, legibility, no truncated text, contrast of at least 4.5:1 for text, and truthful states. Use `web-design` for web criteria.
   - **Pins:** the reference links, the product's existing design tokens, the brand source (for example the app icon), and each taste constraint that the user has stated.
   - **Capture protocol:** the viewport or device, the OS version, light and dark appearance, the largest text size, the language, the seed data and the settle time.
   - **Materiality threshold:** the size of gap that does not justify another round, for example "spacing under 8 pt is not material".
   - **Round limit and stop policy:** a number, for example "round 1 plus at most two fix rounds, then the user decides". Stop on a WIN, on gaps below the threshold, or at the limit.

   Record the bar in the spec's evidence file, or in a design record for the run. Ask the user to confirm or amend the bar before round 1. A request to start, or a missing reference connector, does not remove this step.
5. **Explore, then converge.** Run round 1 through `arena`, with the confirmed bar as its rubric. Its candidates are two or three materially different variants, each labelled, for example a button-state change beside a new screen background (principle-exhaust-the-design-space). `arena` picks one base and grafts the best parts of the other variants into it; from round 2, improve only that base. Build the variants in the product with its existing components; when a component already does the job, reuse it. For a concept, a variant can be a prototype or a generated mock-up that starts from the step 2 captures; label it exploratory, and keep its prompt beside it. Before you polish, cut each element that has no stated user need (principle-earn-every-element).
6. **Run the rounds.** Make one part for each screen or view. Give each builder its own worktree from `scripts/worktree.sh`, and the domain skills in the SKILL.md. When `impeccable` is installed, a builder can use it inside the agreed bar. Give each round's verdict, WIN, LOSE or UNJUDGEABLE, to a fresh critic (principle-judge-with-fresh-eyes), and repair only the single largest gap before the next round. Number the captures of each round. When you report a gap to the user, show the capture of the element that it names.
7. **Fold taste into the bar.** When the user rejects something, record the rejection as a taste constraint in the bar before the next round, and tell the user that the bar changed. Do not judge finished rounds again. A WIN that the user rejects means that the bar was incomplete. For a taste question that no reference settles, get a second view with `taste-review`, and give the user the options with a recommendation. Report the rounds used against the limit. A run that reaches the limit without a WIN ends as LOSE, with its open gaps.
8. **Hand over by entry point.**
   - **Concept:** package the winning design with `design-handover`: each state as a Given/When/Then example beside its visual, labelled exploratory mock-up or prototype capture, with the references and the user's rulings. Then run the Spec playbook with the handover as its input. Do not ship the prototype code.
   - **Spec or polish:** prove the winning design on the real surface. For iOS, also install it on the user's device when one is connected. Record the bar, the ledger and the final captures in the spec's evidence file or in the PR. Continue with Ship in the SKILL.md, with before and after screenshots of each changed state in the PR description.
