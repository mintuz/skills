# Bug fix

A reported defect, often with a screenshot or a recording. Do every step by default. When the user asks you only to diagnose or to recommend a fix, do steps 1, 2, 3 and 7, then report.

Every line that ships traces to runtime evidence. A change that "might help" is a hypothesis, not a fix, and it does not ship. The smallest change that the evidence justifies ships.

1. **Reproduce it yourself, on the branch and on the base.** Drive the matching surface yourself, for example the browser, the simulator or the CLI, with `visual-feedback` for UI. Do this even when a debugging checklist or protocol says to ask the user to reproduce it. Ask the user only after you drive the surface as far as it goes, and only with a specific reason that it cannot reach the target. When the bug does not reproduce on demand, synthesise the trigger, tighten the conditions, or add instrumentation until it fires. For a checkout of the base beside the branch, run `scripts/worktree.sh base <run-id> <base>`. If the base also fails, the branch did not cause the bug; say so. If only the branch fails, find the commit that introduced it. Done when the bug fires on demand, or the reason that it cannot fire is written down.
2. **Test the user's theory.** Treat the theory as one hypothesis. Collect the evidence that could disprove it (principle-attack-the-premise).
3. **Find the root cause by elimination.** List the candidate hypotheses. Seed them with `how` over the affected path and `why` for its regression history. On each pass, run the check that rules out the most remaining hypotheses, and get runtime evidence. When program state is unclear, add logging or instrumentation and read it while the code runs, instead of guessing from the code. Trace the symptom to the first place where the system goes wrong (principle-fix-root-causes). Confirm the surviving mechanism with runtime evidence before you plan the fix. When the evidence refutes a hypothesis, revert every change that the hypothesis motivated. For a long hunt, write its exit predicate first (Long or looping runs in the SKILL.md). For a hard or intermittent cause, such as a race, spawn two agents on different providers with the same brief and reconcile their findings.
4. **Write a failing test.** The test must fail for the reported reason (`tdd`). Commit the failing test before the fix, in its own commit.
5. **Fix the root cause.** Make the smallest change. Prefer a platform feature to new code. When the fix crosses a function boundary and its shape is not settled, run `architect` first.
6. **Prove the fix on the same surface.** The test passes, and the original reproduction on the same surface no longer shows the bug. A passing unit test shows the code path, not that the bug is gone. An inconclusive run, or a check on another surface, for example a Storybook story instead of the running app, is not a pass: report it as a gap, and make the original reproduction run (principle-gaps-are-not-passes). For UI, take screenshots or a recording of the running app before and after the fix.
7. **Search for the same defect.** Look for the same pattern elsewhere. Fix each instance that is in scope, and list the others.
8. **Ship.** Continue with Ship in the SKILL.md.

**Reply:** what was broken, the root cause, the fix, and how you verified it. Paste the failing output and then the passing output of the test and of the reproduction, verbatim.
