# Spec

Write or update a spec with a spec-driven flow such as GitHub Spec Kit, from the agreed behaviour to one PR that holds only the spec. Use it for a new spec, "the full Spec Kit flow" or "the remaining Spec Kit steps". Implementation is a separate request. To draw the examples of an existing spec for review, run step 6 only. The step names are examples, for example `/speckit.specify` or `speckit-specify`; use the commands that the repository installs.

1. **Fix the inputs.** Read the agreed behaviour and its source, the repository's spec rules (constitution, templates, `AGENTS.md` or `CLAUDE.md`), and each active spec that overlaps the capability. Pick a spec number that no other branch uses, and name the spec folder, for example `specs/<NNN>-<slug>/`. For an existing spec, start at the first step whose output is missing or stale, and keep the valid artifacts. Done when one shared context file holds the agreed behaviour, each ruling with its date, the approved examples, the overlapping specs and the skills that the user named.
2. **Store the design evidence in the spec.** Copy every design input into the spec folder: concept images, mock-ups, design exports and screenshots, for example in `designs/` or `screenshots/`. Export each frame that a design tool links to as an image, and keep the link beside it. Label each asset as a design export, an exploratory concept or a running-app capture. Use `design-handover` to pair each asset with the examples or the states that it shows, and list each asset with its pairs in a design references section of `spec.md`. Commit the assets with the spec. Use the shipped product's styles, not the mock-up's. Record an inferred layout as a design assumption, not as a product question. Done when each design input is in the spec folder, labelled and listed in the design references section.
3. **Delegate one step at a time.** Spawn one fresh `adam-agent` for each step, in this order: specify, clarify, plan, tasks, analyze. Add checklist only when the user asks for it. Start a step only after the previous step is committed. Give each agent a cold brief with these fields, and copy them into your plan:
   - **Step:** the step's command, which the agent loads and follows first.
   - **Context:** the shared context file, and the rulings that the step must not reopen.
   - **Folder:** the spec folder, set explicitly for each Spec Kit script instead of another session's feature pointer.
   - **Skills:** the skills that the user named, and `story-splitting` for the user stories. `story-splitting` is an external skill that this repository does not include. When the host does not install it, report the gap.
   - **Files:** the files that the step may change. Do not commit, and do not change an approved example.
   - **Checks:** the repository's spec checks, for example its Spec Kit check and `git diff --check`.
   - **Report:** the files changed, the check results and the open questions; for specify, also the full Given/When/Then set.
4. **Review and commit each step.** Read each step's output yourself before you commit it. Check that each approved example is in the spec word for word, that each cited path exists, and that the step decided no product question. Give each defect, with its reason, to a fresh agent.
5. **Clarify in two phases.** The clarify agent first scans without editing. Sort each question before anyone asks it:
   - a fact that the code or the docs can answer: answer it from the source, and record the answer and its source file in the spec's Clarifications;
   - a question that an earlier ruling or an approved example settles: cite that ruling or example, and do not ask it again;
   - a product decision: ask the user in this form (principle-price-each-option): "Question. Recommended: A, because <reason>. Options: A, <cost>; B, <cost>", with two to four options.

   Ask every product decision that the scan finds, together or in batches, through the host's question tool or in chat. When the user pairs on the spec, ask one question at a time. When the user says "accept the recommendations", list the exact recommendations and record only what the user confirms. Give the user's answers and the sourced answers to a fresh clarify agent, which records them all in a dated Clarifications section. When Spec Kit's clarify command defers a topic because of its own question limit, run clarify again with a fresh agent. Repeat until clarify reports no deferred topic, before plan starts. Record a topic in `spec.md` as an open question with its owner only when the user chooses to defer it.
6. **Draw the examples for review.** After clarify, make a temporary visual document that shows each Given/When/Then example as three pictures, Given, When and Then, beside its words, grouped by user story. The user reviews it on their machine before the merge. The document is a review aid, not a spec artifact: keep it out of every commit and push, do not link it from `spec.md`, and do not mention it in the PR description. Give one fresh `adam-agent` a brief with the fields of step 3, with this step as its Step, and with these rules:
   - **Folder:** the agent writes only in a folder outside every git checkout, for example `~/spec-reviews/<NNN>-<slug>/`. The folder holds one self-contained page, `acceptance-examples.html`, the throwaway script that builds it, and a copy of each asset that the page shows, for example the spec's screenshots.
   - **Words:** the script takes each example's Given, When and Then from `spec.md`, so the page matches it word for word (principle-derive-from-one-owner). The page states that `spec.md` wins when the two differ.
   - **Pictures:** for each Given, When and Then picture, use the stored design asset that shows that state, from the spec's design references (principle-reuse-before-building). Draw a picture in HTML and CSS only when no asset shows the state, or when the asset misses information that the example needs, for example the frames and timing of an animation, a hover, focus, loading or error state, or a measurement. Label each picture as a design, with its file name, or as drawn, with the information that the designs miss. For a drawn picture, use the sizes in the requirements, the product's design tokens and its real icons; when the repository already has a visual-examples page, use it as the template. Draw notes, for example clicks, keys and screen reader speech, over designs and drawings in a style that no product element uses. Label each detail that the spec does not state, for example a person's name (principle-preserve-meaning).
   - **Checks:** look at every example in a browser at desktop width and at 390 px wide. Confirm in the browser that each Given, When and Then on the page is in `spec.md` word for word, and that each picture carries its design or drawn label.
   - **Report:** the page path, the check results, and each gap or contradiction in the spec that the pictures expose, including a design that differs from an example's words. Treat a gap as a question for the spec, not as a fix in the picture.

   Run `double-check` on the page with a model from a different provider, and fix each confirmed finding until the reviewer reports no issues. Then open the page in the user's default browser. When an approved example changes, run the script again.
7. **Record the approval in `spec.md`.** Show the user the complete Given/When/Then set, grouped by user story, with Given, When and Then on separate lines. Give the user the path of the visual document in chat; neither the path nor a link to the document goes into `spec.md`. Write the user's explicit approval of that set, with its date, in `spec.md` before plan starts. A request to run the flow is not approval of the examples. When the user has already approved the set, for example in a reviewed visual document, write that approval in `spec.md` and run the remaining steps without stopping. A change to an approved example resets the approval.
8. **Plan, task and analyze.** Tell the plan agent to ground each owner, path and symbol in the current code, to reuse existing patterns (`reducer`), and to report a contradiction in the spec instead of fixing it. Tell the tasks agent to group the tasks under the user stories, to put a failing test before each behaviour task, and to map each approved example to a task. Run analyze read-only first, and have it mark each finding as a document fix or a product decision. Give the document fixes to a fresh agent, take only the product decisions to the user, then run analyze again to confirm.
9. **Review the spec.** Run the reviews that the repository's rules require. Then run `double-check` on the final artifacts with a model from a different provider, or after each step when the user asks for that. Fix each confirmed finding, and run another round until the reviewer reports no issues. When the rounds stop converging, take the disagreement to the user.
10. **Ship the spec and stop.** Rebase onto the current base, and check again that the spec number is free. Continue with Ship in the SKILL.md, with one PR that holds only the spec artifacts; the auto-merge label and the merge wait for the user's request. In the reply, give the path of the visual document again, so that the user can review it before the merge, and say that the user can delete its folder after the merge. End the reply with the hand-over: implementation runs under Implement, with one `adam-agent` for each user story. When each story ships as its own PR, or the stories depend on each other, add `story-pr-orchestrator` to gate the story PRs; each story still gets its own `adam-agent`.
