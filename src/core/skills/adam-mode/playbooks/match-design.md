# Match design

Make an implementation match a design: mock-up images, a design export or a designer's PR. The design is the spec. Use this playbook for parity work and for each difference that the user reports against the design.

1. **Take the target from the design.** Name the design source for each screen. When a designer's PR has the right look and the wrong implementation, take only its visual target and its assets, such as icons. Implement with the project's own components, tokens and patterns, and with the domain skills in the SKILL.md.
2. **Hold the design fixed.** Never edit the design, a baseline capture, the comparison script or its threshold to make a difference disappear. If the design looks wrong, for example a logo that every other screen has is missing, stop and ask the user or the designer, with the evidence. Continue with the other states meanwhile (principle-never-block-on-the-human), and report the question as an open difference.
3. **List the states.** Before you change code, list every in-scope state of each screen and component: hover, focus, active, disabled, loading, empty, error, the shortest and the longest content, zero, one and many items, and each breakpoint. Done when each state has its design reference, or is marked as missing from the design.
4. **Capture and compare.** For each state, capture the running app with `eyes` and put the capture side by side with the design. Record each difference as one row with four fields: the state, the property, the design value and the app value, and the path of its screenshot. For example: "hover, left padding, design 16px, app 12px, `round1/03-hover.png`". A difference without a screenshot is not recorded. A pixel-exact image diff applies only when the reference is a screenshot of a real implementation. When the reference is a mock-up, tell the user that an image diff against it does not apply, because a mock-up is not a screenshot of a real implementation, and compare state by state.
5. **Change shared primitives first.** Change the shared tokens, icons and base components, and integrate them before any component work. Then make each component its own unit, with its own capture and comparison. Change the units one at a time. To change units in parallel, give each unit one owner and its own worktree: run `scripts/worktree.sh create <run-id> <component>` once for each unit (principle-separate-before-serializing-shared-state).
6. **Loop until no difference remains.** After each change, capture the same state again and compare. Repeat until no difference remains in any listed state. A difference that waits for an answer from step 2 keeps its state unmatched: report it, and do not claim a match for that state.
7. **Show the result.** Add before and after screenshots of each changed state to the PR description. When the user asks for a design handover, use `design-handover`.
8. **Ship.** Continue with Ship in the SKILL.md.
