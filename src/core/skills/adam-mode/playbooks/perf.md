# Perf

Make something measurably faster, or run a performance experiment for a report. Use this playbook on its own, or for a performance user story inside Implement. Each speed claim needs a measurement from the frozen harness. A speed-up that you read from the code is a hypothesis, including "useMemo makes it slower".

1. **Fix the metric and the stop predicate.** Choose the case that reproduces the complaint, one metric and the direction that counts as better. When a spike measured the work, use the spike's scenario. Write a stop predicate that pairs the target with a minimum number of attempts, for example "40% below baseline and at least 8 attempts", so that an early lucky win cannot end the run. Use the user's numbers when they give them.
2. **Build the harness, prove it, freeze it.** Write one repeatable command that prints the median of N runs, the error count and a count of the work done (principle-build-the-lever). Run it on the slow case and on an easy case. If it cannot separate them, change the workload or the metric. Vet it with `benchmark-checklist`, then freeze it. Done when the harness separates the two cases and passes the checklist.
3. **Record the baseline.** Before any change, record the baseline metric and a green run of the regression gate: the tests that must keep passing (principle-capture-the-baseline). Open a decision log outside the tree, for example `/tmp/<run-id>/decision.tsv`, with one row for each attempt: id, hypothesis, change, before, after, delta, gate, verdict. Read the log before each attempt.
4. **Rank the hypotheses.** Use `how` to trace the slow path. Each hypothesis names a mechanism, for example "defer minimap layout until after first paint, because it blocks first paint". Order them by the performance mantras, cheapest first: don't do it; don't do it again; do it less; do it later; do it when they're not looking; do it concurrently; do it cheaper.
5. **Delegate the attempts.** Give each hypothesis to its own `adam-agent` with a tight scope, and review its diff. Run independent hypotheses in parallel, each in its own worktree from `scripts/worktree.sh create <run-id> <unit>`, and measure each one with the same frozen harness against the same baseline. When an attempt crosses a function boundary and its shape is not settled, run `architect` first.
6. **Keep or revert each change.** Each attempt applies one hypothesis to the last kept state. Measure it with the frozen harness and run the gate. Keep it when the metric moves past the noise, or when it removes code and holds the number, and the gate stays green; otherwise revert it in full. Log the row, kept or reverted. Commit each kept change on its own.
7. **Push past the first plateau.** After several reverts in a row, move to another mantra, combine near-misses or try a bolder change. Correctness and simplicity outrank the number: revert a win that breaks behaviour.
8. **Stop on the predicate.** Stop when the predicate holds. Never relax the predicate to meet it. When cheap untried hypotheses remain, continue. When you are stuck, report it.
9. **Encode the budget in CI.** Add a CI check that runs the frozen harness and fails the build when the metric goes above the new baseline plus a margin, for example 10% (principle-encode-lessons-in-structure).
10. **Report the numbers.** When the approach is settled on a spike branch, apply it there and measure the same scenario again. Update the report or the explainer with: the spike that validated the approach, by name; the baseline and the final number; the before and after numbers for each kept change; the attempts kept and reverted; and the log path (principle-explain-the-number). Then continue with Ship in the SKILL.md.
