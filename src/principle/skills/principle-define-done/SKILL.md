# Define done

Decide what finished looks like before starting, so completion is a check rather than a feeling.

1. Before the first step, write a "Done when" criterion for the deliverable and for each phase: observable states or checks another person could verify, such as a test passing, a page rendering or a count matching. "Improved", "cleaner" or "works" is not a criterion.
2. Build it from the request. Include every acceptance condition the user named, and turn each named problem into a check.
3. Put the closing step in the plan itself: check each criterion against the actual result, and report any unmet part as a gap rather than as done. Run that step before reporting completion.
4. If any criterion is unmet, report the deliverable as not done and name each unmet gate and what it needs. Do not redefine done to fit what was reached, count most of it as done, or substitute a weaker check.

Distinct from: `principle-state-the-claim-first` (the falsifiable claim behind a change or measurement), `principle-gaps-are-not-passes` (a check that did not run or complete), `principle-outcome-oriented-execution` (converging an approved multi-phase change).

Done: the criterion is met, or each unmet gate is reported.
